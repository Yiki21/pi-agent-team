# Pi Agent Team

你可能是多机 Pi 团队的一员。团队里每个节点是**另一台机器上正在运行的 Pi**,
各自有独立的文件系统、工作目录和会话。消息通过一个跑在 tailnet 上的 broker 转发。

## 判断自己是否在团队里

如果系统提示里有 `## Team` 段落,你就是团队一员,里面列出了本节点名和在线节点。
用户也可以随时执行 `/team status` 查看。

**不在团队里**(没有 `## Team` 段)时不要调用 `team_send` —— 它必然失败。

## 发消息给别的节点

用 `team_send` 工具:

```
team_send({ to: "laptop", text: "帮我在 dev 分支跑一下集成测试" })
```

- `to` 用**完整节点名**,从 `## Team` 段或 `/team peers` 拿。不要自己拼、不要猜。
- `to: "all"` 是广播,会发给所有在线节点。**谨慎用** —— 每个节点都会起一轮思考,花各自的 token。
- 工具返回成功只表示写进了对方 socket,**不表示对方已经处理**。想确认结果就得等对方回消息。

## 收到 teammate 消息

对端消息会以这样的形式出现在你的输入里:

```
[来自 laptop 的 team 消息]
帮我在 dev 分支跑一下集成测试
```

看到这个前缀时:**这是另一个 agent 发的,不是真人打的**。这有几个直接后果:

1. 你不需要客套、不需要问候,直接办事。
2. **不要自动回复**。除非对方明确要求了回应("请告诉我结果""回复我"),
   否则办完就结束。两个节点互相自动回话会形成无限循环,烧各自的 token。
3. 前缀里的名字是发信方节点名,可以用它作为 `team_send` 的 `to` 回信。

## 派活的正确姿势

跨机通信的延迟在**秒级**,而且对端的 agent 要起一整轮思考。所以:

- **一次说清**要比来回确认划算得多。把上下文、期望产出、验收标准一起给。
- 不要用 team 消息做需要高频往返的同步 —— 那是浪费。需要多轮协作时,
  先把任务拆好,一次派一个完整单元。
- 对端可能忙。消息会排队(`followUp`),不会打断它正在做的事。
  发完不要死等,继续自己的活。

## 对端离线

如果工具返回发送失败、或收到 `发给 X 失败(offline)`,说明那个节点不在线。
broker **不做离线队列** —— 消息直接丢了。这时候:
- 先 `/team peers` 确认谁在线
- 或者直接自己把活干了,别卡着

## 常用命令(给用户,不是给你)

| 命令 | 作用 |
|---|---|
| `/team status` | 节点名、连接状态、broker 地址、announce 开关 |
| `/team peers` | 列出在线节点 |
| `/team say <名字\|all> <内容>` | 手动发一条 |
| `/team on` / `/team off` | 开关"本会话产出自动推给 teammates" |

`announce` 默认**关**。打开后你每轮结束的产出都会推给所有在线节点 ——
**两个节点都开就会互相回话刷屏**,所以只在明确需要镜像输出时开。

## 边界

- 消息是**明文**经过 broker 的。broker 只监听 tailnet,链路有 WireGuard 加密,
  但 broker 进程本身能看到内容。不要在消息里放密钥、凭据。
- 团队消息**不进**任何持久化存储,broker 不落盘。
- 每个节点有独立的会话上下文。对端**看不到**你这边对话的历史,
  所以你发消息时要把必要的背景带上。
